API 压测与上下文缓存观测实践

这是一篇项目内原创长文 fixture，用于稳定构造超过四千 token 的长文本请求。正文关注 API 压测、长上下文、缓存命中率、流式响应和指标口径，适合反复发送以观察上游 context cache。

第 1 轮：长文本缓存观测背景

1.1 在大模型 API 平台的压测中，最容易被误读的指标不是平均延迟，而是请求构成。一个看似很高的吞吐数字，如果混入了模型列表、鉴权探测、失败重试、短文本冒烟或控制面请求，就不能代表真实业务能力。本文把业务请求限定为 chat completions 的成功请求，并把长文本缓存观测从普通吞吐测试中拆出来。这样的拆分会让报告显得更繁琐，但它能避免把不同性质的流量混在同一个分母里，尤其适合评估需要稳定服务在线业务的模型供应商。

1.2 上下文缓存的观测需要比普通压测更谨慎。缓存命中不是请求一发出就天然存在，它依赖上游系统是否已经把某个完整前缀单元持久化。对于第一次请求，服务端通常需要完成完整的 prefill 计算，并在请求边界、输出边界或固定 token 间隔上沉淀可复用的缓存单元。第二次请求如果完全复用上一轮已持久化的前缀，才可能命中。若只是在短 prompt 上观察代理头，或者把所有请求的 usage 聚合在一起，就会得到一个看似精确但含义很模糊的 cache hit rate。

1.3 本文采用的长文本场景是一篇固定文章加一个短问题。固定文章模拟业务中常见的合同审阅、研报摘要、故障复盘、产品文档问答和政策解读。短问题保持稳定，目的是让重复请求的用户输入前缀尽量一致。若要观察 common prefix 规则，也可以保留文章正文不变，只修改末尾问题，让第三次请求命中前两次识别出的公共前缀。为了让命中率口径更清晰，统计时只纳入 prompt_tokens 大于等于四千的请求，短文本基线请求会被排除在 cache hit rate 的分母之外。

1.4 真正的压测流程需要先做冒烟，再做小流量预热，然后再进入阶梯并发。冒烟阶段检查鉴权、模型名、基础非流式请求、流式解析、JSON 输出、工具调用、思考模式和 usage 字段。小流量预热不计入最终门禁，它的作用是让连接池、上游调度和缓存路径进入稳定状态。阶梯并发则按固定用户数逐级运行，每一阶都单独记录成功率、P95、429、5xx、业务 RPM、finish_reason 以及 cache usage。这样做的好处是当某一阶突然劣化时，报告能明确指出拐点，而不是只给出一个长时间平均值。

1.5 业务 RPM 的计算必须保守。只有成功完成的 POST /v1/chat/completions 请求才计入业务 RPM，失败重试、warmup、模型列表、兼容性探测和 cache 专项都不应混入。原因很简单：这些请求的成本和延迟结构不一样，混在一起会掩盖真正的服务能力。短 prompt 的 RPM 往往很高，长 prompt 的 prefill 成本更重，工具调用和思考模式又会引入更多输出 token。把它们拆开后，团队才能知道到底是吞吐不足、长上下文慢、流式首 token 慢，还是某些参数组合不兼容。

1.6 长文本请求的风险在于单次请求资源占用高，稍微提高并发就可能把队列推长。这个时候平均延迟通常失真，因为大量请求仍然在较低延迟完成，少数请求却已经接近超时。P95、P99 和最大延迟更能反映问题。如果 P95 快速上升但错误率还不高，说明服务端可能已经进入排队状态。若同时出现 429，说明限流策略开始介入。若 5xx 增加，说明上游系统可能在资源不足、网关超时或后端异常之间切换。

1.7 上下文缓存的收益主要体现在 prefill 阶段。对于完全相同或高度重叠的长前缀，命中缓存后，服务端可以少做一部分输入侧计算。它不保证输出完全相同，也不会让 decode 阶段消失。因此观察 cache 时不能只看总延迟，还应同时记录 prompt_cache_hit_tokens、prompt_cache_miss_tokens、prompt_tokens、completion_tokens 和 reasoning_tokens。如果模型进入思考模式，输出侧 token 可能大幅增加，掩盖输入侧缓存带来的收益。为了减少变量，缓存专项通常关闭 thinking，并把 max_tokens 控制在较小范围。

1.8 流式响应还需要单独处理首 token 延迟。非流式请求只有总延迟，无法区分模型开始输出之前的等待和持续生成的时间。流式模式下可以记录 TTFT，也就是从请求发出到第一段内容到达的时间。长 prompt 如果没有命中缓存，TTFT 往往更高；命中后 TTFT 有机会下降。不过不同供应商的 SSE 实现并不完全一致，有的会把 JSON chunk 按物理行拆开，有的会在最后追加 usage chunk，有的会省略某些字段。压测工具必须宽容解析，同时在报告里清楚标注解析异常。

1.9 工具调用和 JSON 输出属于兼容性维度，不应默认进入 500 RPM 的业务门禁。工具调用可能触发多轮请求，JSON 输出可能因为 prompt 不够明确而生成空白或被 max_tokens 截断。思考模式会引入 reasoning_content 和 reasoning_tokens，适合专项观察而不是混入基础吞吐。对供应商来说，兼容性 profile 的价值在于暴露协议差异；对业务方来说，throughput profile 的价值在于衡量核心路径容量。两者都重要，但它们回答的问题不同。

1.10 报告的最终目标不是制造一个漂亮的数字，而是让工程团队知道下一步该做什么。如果 cache_hit_rate 在长文本场景下长期为零，就要确认请求前缀是否稳定、prompt_tokens 是否足够长、user_id 是否影响隔离、上游是否返回官方 cache 字段，以及缓存是否需要等待持久化。如果业务 RPM 达不到目标，就要调整用户数、输出长度、thinking 开关和请求权重。如果失败集中在 json_parse，就要检查上游响应编码、代理截断和超时。指标越贴近真实口径，排障越快。

1.11 一个成熟的压测项目应该把配置和代码分离。模型名、base_url、阈值、用户数阶梯、profile 权重、长文本 fixture、cache 最小 prompt token 门槛都应该在配置里调整。代码只负责统一构建请求、记录指标、解析响应和生成 verdict。这样做虽然初期多写了一些框架代码，但后续切换供应商、切换模型、加入新 profile 或收紧阈值时，不需要重新理解整套实现。对于 API 供应商评测来说，这种可重复性比一次性的手工测试更可靠。

1.12 在阅读压测结果时，应优先看失败分类，而不是只看失败率。相同的 2% 失败率，含义可能完全不同：如果都是 429，说明容量或限流配置不足；如果都是 5xx，说明服务稳定性风险更高；如果是 json_parse，可能是代理返回了非标准结构、流式 chunk 被拆分、或者请求超时后网关返回了 HTML；如果是 finish_reason 为 insufficient_system_resource，说明模型推理资源侧已经明确承压。分类清楚后，团队才能把问题交给正确的人。

1.13 长文本缓存还有一个常见误区：认为只要重复请求就一定命中。实际上缓存是 best effort，且持久化需要时间。第一次请求可能只是构造缓存，第二次请求可能还没有完全命中，第三次请求才更容易体现 common prefix 的收益。对于相同长文章加不同问题的模式，前两次请求可能用于让系统识别公共前缀，之后的请求才会命中已持久化的文章前缀。因此 cache suite 应该包含 warmup、wait 和 repeat 三个阶段，而不是只连续发两次就下结论。

1.14 本文所描述的口径适用于 OpenAI compatible API，也适用于许多代理平台，但每家平台的细节都会不同。有的平台会把请求模型名映射成内部模型名，有的平台会在 response.model 中返回后端变体，有的平台会返回 prompt_tokens_details.cached_tokens 而不是 prompt_cache_hit_tokens。压测工具应该同时记录 requested_model 和 response_model，并把官方字段与兼容字段分开标注。这样当模型名出现 high、h、preview 或内部后缀时，不会误以为本地配置写错。

1.15 最后，压测不是一次完成的动作，而是一个逐步收敛的过程。第一轮只需要确认功能和监控路径通；第二轮用小并发观察成功率和延迟；第三轮逐步逼近目标 RPM；第四轮做长跑验证稳定性；第五轮才考虑把 cache 命中率作为硬门禁。每一步都应该保留原始记录、汇总指标和阈值判定。只有这样，当供应商、模型、参数或业务 prompt 发生变化时，团队才能用相同方法复测，而不是从头争论指标含义。

3.1 在大模型 API 平台的压测中，最容易被误读的指标不是平均延迟，而是请求构成。一个看似很高的吞吐数字，如果混入了模型列表、鉴权探测、失败重试、短文本冒烟或控制面请求，就不能代表真实业务能力。本文把业务请求限定为 chat completions 的成功请求，并把长文本缓存观测从普通吞吐测试中拆出来。这样的拆分会让报告显得更繁琐，但它能避免把不同性质的流量混在同一个分母里，尤其适合评估需要稳定服务在线业务的模型供应商。

3.2 上下文缓存的观测需要比普通压测更谨慎。缓存命中不是请求一发出就天然存在，它依赖上游系统是否已经把某个完整前缀单元持久化。对于第一次请求，服务端通常需要完成完整的 prefill 计算，并在请求边界、输出边界或固定 token 间隔上沉淀可复用的缓存单元。第二次请求如果完全复用上一轮已持久化的前缀，才可能命中。若只是在短 prompt 上观察代理头，或者把所有请求的 usage 聚合在一起，就会得到一个看似精确但含义很模糊的 cache hit rate。

3.3 本文采用的长文本场景是一篇固定文章加一个短问题。固定文章模拟业务中常见的合同审阅、研报摘要、故障复盘、产品文档问答和政策解读。短问题保持稳定，目的是让重复请求的用户输入前缀尽量一致。若要观察 common prefix 规则，也可以保留文章正文不变，只修改末尾问题，让第三次请求命中前两次识别出的公共前缀。为了让命中率口径更清晰，统计时只纳入 prompt_tokens 大于等于四千的请求，短文本基线请求会被排除在 cache hit rate 的分母之外。

3.4 真正的压测流程需要先做冒烟，再做小流量预热，然后再进入阶梯并发。冒烟阶段检查鉴权、模型名、基础非流式请求、流式解析、JSON 输出、工具调用、思考模式和 usage 字段。小流量预热不计入最终门禁，它的作用是让连接池、上游调度和缓存路径进入稳定状态。阶梯并发则按固定用户数逐级运行，每一阶都单独记录成功率、P95、429、5xx、业务 RPM、finish_reason 以及 cache usage。这样做的好处是当某一阶突然劣化时，报告能明确指出拐点，而不是只给出一个长时间平均值。

3.5 业务 RPM 的计算必须保守。只有成功完成的 POST /v1/chat/completions 请求才计入业务 RPM，失败重试、warmup、模型列表、兼容性探测和 cache 专项都不应混入。原因很简单：这些请求的成本和延迟结构不一样，混在一起会掩盖真正的服务能力。短 prompt 的 RPM 往往很高，长 prompt 的 prefill 成本更重，工具调用和思考模式又会引入更多输出 token。把它们拆开后，团队才能知道到底是吞吐不足、长上下文慢、流式首 token 慢，还是某些参数组合不兼容。

3.6 长文本请求的风险在于单次请求资源占用高，稍微提高并发就可能把队列推长。这个时候平均延迟通常失真，因为大量请求仍然在较低延迟完成，少数请求却已经接近超时。P95、P99 和最大延迟更能反映问题。如果 P95 快速上升但错误率还不高，说明服务端可能已经进入排队状态。若同时出现 429，说明限流策略开始介入。若 5xx 增加，说明上游系统可能在资源不足、网关超时或后端异常之间切换。

3.7 上下文缓存的收益主要体现在 prefill 阶段。对于完全相同或高度重叠的长前缀，命中缓存后，服务端可以少做一部分输入侧计算。它不保证输出完全相同，也不会让 decode 阶段消失。因此观察 cache 时不能只看总延迟，还应同时记录 prompt_cache_hit_tokens、prompt_cache_miss_tokens、prompt_tokens、completion_tokens 和 reasoning_tokens。如果模型进入思考模式，输出侧 token 可能大幅增加，掩盖输入侧缓存带来的收益。为了减少变量，缓存专项通常关闭 thinking，并把 max_tokens 控制在较小范围。

3.8 流式响应还需要单独处理首 token 延迟。非流式请求只有总延迟，无法区分模型开始输出之前的等待和持续生成的时间。流式模式下可以记录 TTFT，也就是从请求发出到第一段内容到达的时间。长 prompt 如果没有命中缓存，TTFT 往往更高；命中后 TTFT 有机会下降。不过不同供应商的 SSE 实现并不完全一致，有的会把 JSON chunk 按物理行拆开，有的会在最后追加 usage chunk，有的会省略某些字段。压测工具必须宽容解析，同时在报告里清楚标注解析异常。

3.9 工具调用和 JSON 输出属于兼容性维度，不应默认进入 500 RPM 的业务门禁。工具调用可能触发多轮请求，JSON 输出可能因为 prompt 不够明确而生成空白或被 max_tokens 截断。思考模式会引入 reasoning_content 和 reasoning_tokens，适合专项观察而不是混入基础吞吐。对供应商来说，兼容性 profile 的价值在于暴露协议差异；对业务方来说，throughput profile 的价值在于衡量核心路径容量。两者都重要，但它们回答的问题不同。

3.10 报告的最终目标不是制造一个漂亮的数字，而是让工程团队知道下一步该做什么。如果 cache_hit_rate 在长文本场景下长期为零，就要确认请求前缀是否稳定、prompt_tokens 是否足够长、user_id 是否影响隔离、上游是否返回官方 cache 字段，以及缓存是否需要等待持久化。如果业务 RPM 达不到目标，就要调整用户数、输出长度、thinking 开关和请求权重。如果失败集中在 json_parse，就要检查上游响应编码、代理截断和超时。指标越贴近真实口径，排障越快。

3.11 一个成熟的压测项目应该把配置和代码分离。模型名、base_url、阈值、用户数阶梯、profile 权重、长文本 fixture、cache 最小 prompt token 门槛都应该在配置里调整。代码只负责统一构建请求、记录指标、解析响应和生成 verdict。这样做虽然初期多写了一些框架代码，但后续切换供应商、切换模型、加入新 profile 或收紧阈值时，不需要重新理解整套实现。对于 API 供应商评测来说，这种可重复性比一次性的手工测试更可靠。

3.12 在阅读压测结果时，应优先看失败分类，而不是只看失败率。相同的 2% 失败率，含义可能完全不同：如果都是 429，说明容量或限流配置不足；如果都是 5xx，说明服务稳定性风险更高；如果是 json_parse，可能是代理返回了非标准结构、流式 chunk 被拆分、或者请求超时后网关返回了 HTML；如果是 finish_reason 为 insufficient_system_resource，说明模型推理资源侧已经明确承压。分类清楚后，团队才能把问题交给正确的人。

3.13 长文本缓存还有一个常见误区：认为只要重复请求就一定命中。实际上缓存是 best effort，且持久化需要时间。第一次请求可能只是构造缓存，第二次请求可能还没有完全命中，第三次请求才更容易体现 common prefix 的收益。对于相同长文章加不同问题的模式，前两次请求可能用于让系统识别公共前缀，之后的请求才会命中已持久化的文章前缀。因此 cache suite 应该包含 warmup、wait 和 repeat 三个阶段，而不是只连续发两次就下结论。

3.14 本文所描述的口径适用于 OpenAI compatible API，也适用于许多代理平台，但每家平台的细节都会不同。有的平台会把请求模型名映射成内部模型名，有的平台会在 response.model 中返回后端变体，有的平台会返回 prompt_tokens_details.cached_tokens 而不是 prompt_cache_hit_tokens。压测工具应该同时记录 requested_model 和 response_model，并把官方字段与兼容字段分开标注。这样当模型名出现 high、h、preview 或内部后缀时，不会误以为本地配置写错。

3.15 最后，压测不是一次完成的动作，而是一个逐步收敛的过程。第一轮只需要确认功能和监控路径通；第二轮用小并发观察成功率和延迟；第三轮逐步逼近目标 RPM；第四轮做长跑验证稳定性；第五轮才考虑把 cache 命中率作为硬门禁。每一步都应该保留原始记录、汇总指标和阈值判定。只有这样，当供应商、模型、参数或业务 prompt 发生变化时，团队才能用相同方法复测，而不是从头争论指标含义。
